## 1. The big picture

TigerQuest is a **static website**: three code files and one image. Everything runs **inside the student's browser**. There is no server of our own and no database.

```text
┌───────────────────────────── Student's browser (Chrome) ─────────────────────────────┐
│                                                                                       │
│  index.html ──► structure (what's on the page)                                        │
│  style.css  ──► appearance & layout (how it looks)                                    │
│  script.js  ──► behavior (what happens when you click, type, or load)                 │
│      │                                                                                │
│      ├── Game data: BUILDINGS, missions, WAYPOINTS, sample events (JS objects)        │
│      ├── Map: <svg> + <image> + transparent building polygons                         │
│      ├── Game loop: requestAnimationFrame → move character → redraw                   │
│      ├── Pathfinding: Dijkstra's algorithm over the waypoint graph                    │
│      ├── localStorage ◄──► saved missions, XP inputs, saved events                    │
│      │                                                                                │
│      └── fetch() ──── HTTPS GET ─────────────────────────────┐                        │
└──────────────────────────────────────────────────────────────┼────────────────────────┘
                                                               ▼
                                   events.towson.edu  (Towson's public events calendar)
                                   returns JSON: this week's events
```

**Frontend vs. backend**
- The **frontend** is everything that runs in the user's browser: the page, its looks, its logic. TigerQuest is 100% frontend.
- A **backend** is a program running on a server that many users talk to, usually with a **database**. It's needed when data must be shared, trusted or kept secret (accounts, verified XP, private API keys).

**Why no backend?** For a prototype where each student's progress only needs to stay on their own device, and event data comes from a public calendar that already allows browser access, a backend would add cost and complexity without adding demo value. Section 12 explains where that changes.

## 2. Technologies we actually use

| Technology | What it is | What problem it solves for us | How TigerQuest uses it | Alternatives | Why we didn't need them |
|---|---|---|---|---|---|
| **HTML** | The language that describes a page's structure | Defines what exists on the screen | `index.html`: top bar, nav buttons, sidebars, the `<svg>` map, and the Skills/Missions/This Week/Progress screens | Templates generated by a framework (React JSX, etc.) | One page with fixed regions; plain HTML is clearer |
| **CSS** | Styling language | Colors, spacing, layout, mobile vs. desktop | `style.css`: the navy and gold game theme, a **CSS Grid** three-column layout, **Flexbox** inside panels, **media queries** for tablet and phone, hover and selected states for buildings | Tailwind, Bootstrap | No extra library to learn or load |
| **JavaScript** | The browser's programming language | Makes the page interactive | `script.js`: data, rendering, pathfinding, movement, missions, XP, events, saving | TypeScript, React, Vue | No build step; runs by double-click; easier to explain |
| **SVG** | Vector graphics described in markup; shapes are real page elements | Makes regions of a picture clickable, keeps everything aligned while scaling | The map `<svg>` contains the map `<image>`, 11 transparent `<polygon>` hotspots, the character, and 📅 badges | HTML `<map>`/`<area>`, `<canvas>`, a game engine | SVG shapes can be styled, focused with the keyboard, and scale with the picture automatically |
| **JSON** | A text format for data: `{ "title": "…" }` | The event calendar sends data in it | `response.json()` turns the calendar's reply into JavaScript objects. We also store our save data as JSON text in `localStorage` | XML, CSV | It's what the API returns, and JavaScript reads it natively |
| **HTTP / Fetch API** | How browsers request data from servers; `fetch()` is the built-in function for it | Getting real events | `loadLiveEvents()` sends `GET https://events.towson.edu/api/2/events?...` | `XMLHttpRequest`, axios | `fetch()` is built in and simple |
| **External events API** | Towson's public calendar (Localist platform) | Real, current opportunities | Read-only, no API key | Involved@TU, hand-entered data | See section 6 |
| **localStorage** | Small key → text storage built into each browser | Remember progress without a database | Key `tigerquest-save-v2` holds mission states and saved events | Firebase, PostgreSQL, cookies | No accounts are needed for a prototype |
| **requestAnimationFrame** | Browser API that calls your function before each screen repaint (~60×/s) | Smooth animation | `gameLoop()` moves and redraws the character every frame | `setInterval`, animation libraries | Smoother, pauses in background tabs, built in |
| **Intl.DateTimeFormat** | Built-in date formatting with time zones | "This week" must mean Towson's week, not the viewer's | `todayInNewYork()` gets today's date in America/New_York | Date libraries (moment, luxon) | One built-in call is enough |

**Not used** (sometimes assumed): no React or other framework, no Node.js server, no npm packages, no database, no game engine, no login system, no Involved@TU integration.

## 3. What happens when you open index.html

🟢 **Simple:** the browser reads the page, applies the styles, then runs our script. The script draws the buildings, restores your progress, starts the animation loop, and quietly asks Towson's calendar for this week's events.

🔵 **Technical, step by step:**

1. **HTML is parsed.** The browser builds the **DOM** (a tree of page elements) from `index.html`.
2. **CSS is loaded** from `<link rel="stylesheet" href="style.css">` and applied.
3. **The map image** loads from `assets/towson-campus-map.png` (a relative path, so it works on any computer).
4. **`script.js` runs** (a classic `<script>`, not a module, which is why double-clicking works over `file://`).
   - Top of file: the data objects are created (`CATEGORIES`, `BUILDINGS`, `WAYPOINTS`, `PATH_LINKS`, `SAMPLE_EVENT_TEMPLATES`).
   - The last line calls **`init()`** (line ~1418):

```js
function init() {
  save = loadSave();                 // 1. restore progress from localStorage
  week = getCurrentWeek();           // 2. Monday–Sunday in New York time
  sampleEvents = buildSampleEvents();// 3. demo events dated to this week
  renderHotspots();                  // 4. draw 11 clickable building polygons
  renderCategoryList();
  renderEventBadges();
  renderDebugLayer();                // only if the URL ends in #debug
  updateAll();                       // 5. fill all panels/screens
  setupEventHandlers();              // 6. connect clicks to functions
  setupKeyboard();
  requestAnimationFrame(gameLoop);   // 7. start the game loop
  loadLiveEvents();                  // 8. fetch live events in the background
}
```

5. **The user interacts.** Every click or key press triggers an **event listener**, which calls a function such as `selectBuilding()`. That function changes **state** (variables like `selectedBuildingId`) and then re-renders the affected HTML.

**How the interface updates:** functions like `renderDetails()`, `renderJournal()` and `renderWeekScreen()` build HTML strings from the data and assign them to `element.innerHTML`. After any progress change, `updateAll()` re-renders everything that depends on it. This is simple "client-side rendering" without a framework.

**Event delegation:** many buttons are re-created on every render, so instead of attaching a listener to each one, `setupEventHandlers()` (line ~1357) adds **one** click listener on the whole document and checks the clicked button's `data-*` attributes:

```js
document.addEventListener('click', event => {
  const target = event.target.closest('button');
  ...
  if (data.missionAction) handleMissionAction(data.mission, data.missionAction);
  else if (data.saveEvent) toggleSavedEvent(data.saveEvent);
  else if (data.showEvent) showEventOnMap(data.showEvent);
  ...
});
```

## 4. The interactive campus map

🟢 **Simple:** the map is a picture. On top of each building we placed an invisible shape with the same outline. Clicking the shape tells the program which building you picked.

🔵 **Technical:**
- `index.html` contains `<svg viewBox="0 0 1511 1041">` with `<image href="assets/towson-campus-map.png" width="1511" height="1041">`. Because the **viewBox equals the image's pixel size, one SVG unit = one pixel of the original picture.** This is our **coordinate system**: (0, 0) is the top-left corner, x grows to the right, y grows downward.
- Each building in `BUILDINGS` (line ~57) has an `area`, a list of corner points traced over the artwork:

```js
{ id: 'cook', name: 'Cook Library / Media Center', abbr: 'CK/MC',
  area: [[1052,345],[1090,285],[1296,282],[1292,430],[1056,428]],
  door: { x: 1185, y: 508 },
  categories: ['academic', 'communication'], ... }
```

- `renderHotspots()` (line ~668) turns each building into
  `<g class="hotspot" role="button" tabindex="0" data-building="cook" aria-label="…"><polygon class="hit" points="…"/></g>`.
  The polygon's fill is fully transparent, so it's invisible but still clickable. **`data-building` is the link between the shape and the building's data.**
- **Selection:** a click or Enter/Space calls `selectBuilding(id, …)` (line ~749). It sets `selectedBuildingId`, calls `renderMapState()`, which adds the CSS class `selected` (gold outline and glow in `style.css`) and `faded` to buildings that don't match the current filter, then calls `renderDetails()` to fill the right panel.
- **Resizing:** the whole SVG scales as one unit, so the picture, polygons, character and badges always stay aligned. `preserveAspectRatio="xMidYMid meet"` fits the full picture inside the available space without stretching or cropping.
- **Click → map coordinates:** `screenToMap()` (line ~646) converts a mouse position to map pixels using the SVG's own transformation matrix (`getScreenCTM().inverse()`). This works at any size and any zoom.
- **Construction cone:** it is **part of the illustration itself**. There is no code for it; it's decorative and not an obstacle.
- **Event badges:** `renderEventBadges()` (line ~717) counts this week's events per `buildingId` and draws a small "📅 N" box at each building outline's top-left corner (found with `polygonBounds()`).
- **Zoom:** `updateCamera()` (line ~595) changes the SVG `viewBox` to show a smaller window around the player. Zooming is just "showing a smaller part of the same coordinate system".

🐯 **Example:** you click the yellow Cook Library building. The browser fires a click on the polygon with `data-building="cook"`, then `selectBuilding('cook', {walk: true})` highlights it, fills the panel with Cook's services, events and missions, and starts the walk to `door: {x: 1185, y: 508}`.

📂 `index.html` (the `<svg>`), `script.js`: `BUILDINGS`, `renderHotspots`, `renderMapState`, `selectBuilding`, `renderDetails`, `renderEventBadges`, `screenToMap`, `updateCamera`. `style.css`: `.hotspot`, `.hit`, `.selected`, `.faded`.

🤔 **Why:** SVG polygons give exact outlines (not just rectangles), keyboard focus, CSS styling and automatic scaling, all built into the browser. A `<canvas>` or game engine would require us to re-implement clicking, scaling and accessibility ourselves.

**Debug view:** open `index.html#debug` to see the outlines (red), door points (green) and walking network (blue). `renderDebugLayer()` draws them.

## 5. Character movement & pathfinding

*This is the most technical part of TigerQuest.*

### 5.1 Position and coordinates
🟢 The character is just a dot at an (x, y) spot on the map, drawn as a little student.
🔵 `const player = { x: 700, y: 640, route: [], facing: 1, walking: false };` (line ~512). `drawPlayer()` moves the SVG group with `transform="translate(x y)"`. Coordinates are **map pixels**, not screen pixels, so the position stays correct when the window is resized.

### 5.2 Waypoints and the graph
🟢 We placed **43 invisible dots** on the paths of the illustration and listed which dots are connected by a walkable straight line, like a hand-drawn subway map of campus.

🔵 This is a **graph**:
- **Nodes** = waypoints: `WAYPOINTS = { a:{x:60,y:290}, b:{x:200,y:288}, … }` (line ~222)
- **Edges** = connections: `PATH_LINKS = [['a','b'], ['b','c'], …]` (line ~233)
- **Edge weight** = straight-line distance between the two points: `Math.hypot(dx, dy)`
- `NEIGHBORS` (line ~244) turns the edge list into a lookup table, e.g. `NEIGHBORS.m = ['aq','n','aa']`.
- Each building has a **door** point where the character stops.

### 5.3 Can I walk in a straight line? (collision checks)
- `isPointInPolygon(point, polygon)` (line ~413) uses the classic **ray-casting** test: imagine a line going right from the point and count how many building edges it crosses. An odd count means the point is inside.
- `isSegmentClear(a, b)` (line ~435) checks points every 8 pixels along a line. If any of them is inside a building, the line is blocked:

```js
function isSegmentClear(a, b) {
  const steps = Math.max(1, Math.ceil(distance(a, b) / 8));
  for (let i = 0; i <= steps; i++) {
    const t = i / steps;
    if (isInsideAnyBuilding({ x: a.x + (b.x - a.x) * t, y: a.y + (b.y - a.y) * t })) return false;
  }
  return true;
}
```

### 5.4 Dijkstra's algorithm
🟢 **Simple:** Dijkstra's algorithm finds the shortest route through a network. It starts at your position and keeps expanding outward to the **closest place it hasn't finished yet**, writing down the best distance to each spot and which spot it came from. When it reaches the destination, it follows those notes backwards to get the route.

🔵 **Technical** (`findPath(from, to)`, line ~460):
1. **Shortcut:** if `isSegmentClear(from, to)`, return `[to]` and walk straight.
2. Add two temporary nodes: **START** (the player) and **END** (the door). START connects to every waypoint it can "see" without crossing a building, and every waypoint that can see END connects to END.
3. Set `shortest[START] = 0` and every other node to `Infinity`.
4. Repeat: pick the unvisited node with the smallest `shortest` value (`current`). Mark it visited. For each neighbor, if `shortest[current] + distance(current, neighbor)` is smaller than `shortest[neighbor]`, update it and remember `previous[neighbor] = current`.
5. Stop when END is picked. Walk `previous[]` backwards from END to START to build the route.
6. If END was never reached, fall back to walking straight.

```js
while (unvisited.size > 0) {
  let current = null;
  unvisited.forEach(id => { if (current === null || shortest[id] < shortest[current]) current = id; });
  if (shortest[current] === Infinity || current === 'END') break;
  unvisited.delete(current);
  neighborsOf(current).forEach(next => {
    const viaCurrent = shortest[current] + distance(points[current], points[next]);
    if (viaCurrent < shortest[next]) { shortest[next] = viaCurrent; previous[next] = current; }
  });
}
```

**Why Dijkstra?** Edges have different lengths, and Dijkstra guarantees the shortest total distance when all weights are positive. Breadth-first search would minimize the *number of hops*, not the distance. A* would be faster on huge maps, but with about 45 nodes Dijkstra takes about a millisecond (measured below 1.5 ms in our test) and is easier to explain. We use a simple loop to find the closest node instead of a priority queue; that's fine at this size.

### 5.5 🐯 Worked examples (computed by running our actual `findPath` code)

**University Union → Cook Library:** the straight line from the Union door (440, 584) to the Cook door (1185, 508) crosses the open lawn and touches no building outline, so step 1's shortcut applies: **route = [Cook door]**, about 749 map pixels, roughly 2.5 seconds at 300 px/s. Dijkstra isn't needed.

**University Union → Liberal Arts** (where Dijkstra matters): a straight line would cut through Hawkins Hall. Dijkstra returns:

```text
UU door (440,584) → waypoint n (808,505) → waypoint ao (809,370) → LA door (842,248)
```

Waypoint `n` is on the path below Hawkins/Lecture Hall, and `ao` is in the narrow gap *between* Hawkins Hall and Lecture Hall. The total is about 638 px. The character walks around the buildings instead of through them.

### 5.6 The game loop and requestAnimationFrame
🟢 Like a flip-book: about 60 times per second we move the character a tiny bit and redraw it.

🔵 `gameLoop(now)` (line ~608) is called by `requestAnimationFrame` before every screen repaint:

```js
function gameLoop(now) {
  const seconds = lastFrameTime === null ? 0 : Math.min(0.05, (now - lastFrameTime) / 1000);
  lastFrameTime = now;
  const { dx, dy } = getKeyboardDirection();
  if (dx !== 0 || dy !== 0) {
    player.route = [];                          // keyboard cancels automatic walking
    player.walking = moveManually(dx, dy, seconds);
  } else if (player.route.length > 0) {
    player.walking = followRoute(seconds);
  } else {
    player.walking = false;
  }
  drawPlayer(now);
  updateCamera();
  requestAnimationFrame(gameLoop);              // ask for the next frame
}
```

- Distance moved = **speed × seconds since last frame** (`AUTO_WALK_SPEED = 300`, `MANUAL_WALK_SPEED = 240` px/s). So the character moves at the same speed on fast and slow computers.
- `followRoute()` moves toward `route[0]` and removes each point when it's reached.
- While walking, `drawPlayer()` adds a small bounce and lean. With the OS "reduce motion" setting, the walk is 2.5× faster with no bounce.

### 5.7 Keyboard controls, interruption, collisions, boundaries
- `setupKeyboard()` (line ~627): `keydown` adds a direction (`'up'`, `'left'`, …) to the `keysHeld` set, and `keyup` removes it. `KEY_DIRECTIONS` maps `w`/`ArrowUp` → up, and so on. Keys are ignored while typing in the search box or when not on the Map tab. When the window loses focus, all keys are released, so no key gets "stuck".
- **Diagonals:** `getKeyboardDirection()` multiplies by `Math.SQRT1_2` (≈0.707) when two directions are held, so diagonal speed isn't faster.
- **Interruption:** any held key clears `player.route`. Clicking another building calls `walkTo()`, which replaces the route.
- **Collisions:** `moveManually()` tries the full move. If the new spot is inside a building, it tries moving only horizontally, then only vertically, which lets the character slide along walls.
- **Boundaries:** `isWalkable()` rejects points outside the map edges (with a small margin).

📂 `script.js` sections 4–6. 🤔 A hand-made graph is small enough to understand completely and debug visually (`#debug`), and it needs no library.

## 6. Live events integration

### 6.1 Which source?
| | Towson **Events Calendar** (`events.towson.edu`) | **Involved@TU** (`involved.towson.edu`) |
|---|---|---|
| Platform | Localist | Campus Labs Engage |
| Used by TigerQuest? | ✅ **Yes** | ❌ **No** |
| Why / why not | Public, documented Localist API; no key; allows browser requests (CORS `*`) | RSS covers only about the next 24 h; the JSON endpoint is undocumented and blocked by CORS; the official API needs institutional credentials |

**Endpoint:** `https://events.towson.edu/api/2/events?start=YYYY-MM-DD&end=YYYY-MM-DD&pp=100&page=1` (constant `LIVE_EVENTS_API`, line ~275). Localist publishes documentation for this API. We did **not** review the calendar's terms of use. See PROJECT_LIMITATIONS.

### 6.2 HTTP, fetch() and JSON
🟢 The browser sends a message to Towson's calendar: "give me this week's events." The calendar replies with a text list in JSON format, which our code turns into event cards.

🔵 `loadLiveEvents()` (line ~1042) is an `async` function:

```js
const response = await fetch(url, { signal: controller.signal }); // HTTP GET
if (!response.ok) throw new Error('HTTP ' + response.status);
const data = await response.json();                               // JSON text → JS objects
all = all.concat(data.events || []);
```

- `fetch()` returns a **Promise**, a placeholder for a result that arrives later. `await` pauses only this function, so the rest of the app stays usable.
- An `AbortController` cancels the request after **8 seconds**.
- Up to 3 pages of 100 events are requested.
- **JSON** looks like `{"events":[{"event":{"title":"…","location_name":"University Union","event_instances":[…]}}]}`.

### 6.3 CORS in plain language
Browsers protect users by stopping a web page from reading data from *other* websites unless that website says "this is OK". The website says so with an HTTP header: **`Access-Control-Allow-Origin`**. Towson's events API sends `Access-Control-Allow-Origin: *` ("any site may read this public data"), so our page can read it, **even when opened by double-clicking** (a `file://` page). We tested that in Chrome. Involved@TU's JSON endpoint does **not** send this header, so the browser blocks it. We did not try to get around this.

### 6.4 From raw data to TigerQuest events
`convertLiveEvent(item)` (line ~1012) turns each calendar item into our simple shape:

```js
{ id, title, description, date, dates, startTime, endTime, allDay,
  location, buildingId, categories, host, url, source: 'live' }
```

- **Date filtering:** `getCurrentWeek()` finds Monday–Sunday in America/New_York (`todayInNewYork()` uses `Intl.DateTimeFormat('en-CA', { timeZone: 'America/New_York' })`, which formats as `YYYY-MM-DD`). Only event instances whose date falls in that range are kept. Dates are compared as `"YYYY-MM-DD"` text, which sorts correctly and avoids time-zone bugs.
- **Times:** the calendar already sends New York times (`"2026-11-10T11:00:00-05:00"`), so we read `HH:MM` directly.
- **Location → building:** `guessBuildingId()` tests `LOCATION_RULES` (line ~967), regular expressions such as `/university union|\buu\s?\d/` → `union` and `/center for the arts|\bca\s?\d{3,4}/` → `arts`. **If nothing matches, `buildingId` is `null`** and the event is listed as "Not on the TigerQuest map". We never assign an unclear location to a building.
- **Categories:** `guessCategories()` looks for keywords in the event's types, departments and title (e.g. "career", "exhibit"), keeping at most 2. If none match, it defaults to Community.
- **Safety:** all event text is passed through `escapeHTML()` before being placed in the page, so text from the calendar can't inject HTML. Links must start with `https://` (`safeUrl()`).

### 6.5 Display, Show on Map, saving
- `renderWeekScreen()` (line ~1129) applies category and day filters, lists upcoming events grouped by day, and puts "Earlier this week" events last.
- **Show on map** → `showEventOnMap(id)` (line ~1098): sets `selectedEventId`, then `selectBuilding(event.buildingId, { walk: true, openSheet: true })`. That switches to the Map tab, highlights the building, walks the character there, and `renderDetails()` puts the selected event first and highlights it.
- **Add to My Quests** → `toggleSavedEvent(id)` (line ~1083) stores a **copy** of the event in `save.savedEvents`, so it still shows offline. Saving never gives XP.

### 6.6 When the network fails
If `fetch` throws (offline, DNS failure, timeout, HTTP error), `liveStatus = 'failed'` and the app keeps showing **sample events** generated by `buildSampleEvents()` (line ~946) from `SAMPLE_EVENT_TEMPLATES`. Each template has a `day` number (0 = Monday), so sample dates always fall in the current week. Every sample card says **🧪 SAMPLE DATA**, and a note explains that the live calendar couldn't be reached. We tested this by blocking `events.towson.edu`.

**Reliability concerns:** the external service can change or go down, and keyword matching can be wrong. See PROJECT_LIMITATIONS §2.4–2.5.

## 7. Missions, XP and levels

🟢 Each building has real-world missions. Doing one (and having it verified) earns XP, which raises your level and your skill bars.

🔵 **Data:** missions live inside each building:

```js
{ id: 'uni1', name: 'Career Quest: Resume Check',
  desc: 'Meet a Career Center coach or attend a resume review.',
  skills: { career: 150, communication: 50 }, icon: '💼' }
```

- `ALL_MISSIONS` flattens them and adds `buildingId` (27 missions, 3,610 XP possible).
- **Categories** are the 7 keys in `CATEGORIES`: academic, career, communication, social (shown as "Community"), leadership, wellness, creative.
- **XP reward** = sum of the `skills` values (`missionXp()`, line ~363). `uni1` = 150 + 50 = **200 XP**: 150 toward Career and 50 toward Communication. One mission can feed two skills without double counting.

**Mission states** are stored in `save.missionStates`:

| State | Button | XP |
|---|---|---|
| Available | default (not stored) | 0 |
| Planned | 📌 Plan it | 0 |
| Self-reported | ✋ I did this | 0 |
| Verified | ⚡ Simulate verified completion | ✅ full XP |

`handleMissionAction()` (line ~861) changes the state, saves, and calls `updateAll()`.

**Duplicate prevention:** XP is never "added" to a running total. It's **recalculated** from the mission states every time:

```js
function getTotalXp(fromSave = save) {
  return ALL_MISSIONS
    .filter(m => fromSave.missionStates[m.id] === 'verified')
    .reduce((sum, m) => sum + missionXp(m), 0);
}
```

A mission is either verified or not, so it can only count once. `handleMissionAction` also returns early if the mission is already verified.

**Levels** (`xpNeededForNextLevel`, `getLevelInfo`, lines ~385–400), with the same numbers as our first prototype: level 1→2 costs **350 XP**, and after that level L→L+1 costs **350 + 90 × L** (2→3: 530, 3→4: 620, 4→5: 710). `getLevelInfo` subtracts each level's cost until the XP runs out.

🐯 **Example (checked by running the code):** verify `uni1` (200 XP) + `west1` (100) + `uni2` (150) = **450 XP**. 450 − 350 = 100, so you are **Level 2 with 100 / 530 XP** toward Level 3.

**Why arriving at a building doesn't complete a mission:** the virtual walk is for *discovery*. TigerQuest rewards real-world action. Auto-completing on arrival would reward clicking, not growing. Verification is **simulated** in this prototype (see PROJECT_LIMITATIONS §1).

## 8. Saving progress with localStorage

🟢 The browser has a small notebook for each website. We write your progress in it, so it's still there after a refresh.

🔵 `localStorage` is a key → text store, private to one browser on one device, for one site (for files opened directly, browsers treat local files as their own "site"). It is **not a database**: there are no queries, no sharing between users, it holds only a few megabytes, and the user can see and edit it.

**What we store** (one key, `tigerquest-save-v2`):

```json
{
  "version": 2,
  "missionStates": { "uni1": "verified", "cook2": "planned" },
  "savedEvents": [ { "id": "live-536…", "title": "Baltimore Writers' Conference", "...": "..." } ],
  "summary": { "totalXp": 200, "level": 1, "skillXp": { "career": 150, "...": 0 } }
}
```

`summary` is a convenience copy. XP and level are **always recalculated** from `missionStates` when the app loads.

**Loading** (`loadSave()`, line ~321):
1. Read `tigerquest-save-v2`. If present, `JSON.parse` it and pass it through `cleanSave()`, which keeps only known mission IDs, valid states and well-formed saved events.
2. If not present but the **old prototype's key** `tigerquest-prototype-v1` exists (`{completed: [...]}`), `migrateFromVersion1()` turns those missions into `verified`, so old progress is kept.
3. Any error, such as corrupted JSON, is caught with `try/catch`, and the app starts fresh instead of crashing. We tested this with deliberately broken data.

**Saving:** `writeSave()` (line ~337) runs `JSON.stringify` and `localStorage.setItem`, also inside `try/catch`, because storage can be blocked.

**Reset:** Progress → "Reset all progress" → `resetProgress()` asks `confirm()`. On OK, it empties the save and removes both keys.

**Clearing browser data** or using another browser or device means starting over. That's the main tradeoff of not having accounts.

## 9. Layout & responsive design

- **Desktop (≥ 1151 px):** a CSS Grid with three columns (left sidebar, map, right sidebar). `.app` is exactly one viewport tall (`height: 100dvh`). The sidebars have `overflow-y: auto`, so they **scroll independently**, while the map stays in the center. `min-height: 0` on the grid and flex children is essential: without it, children grow to fit their content and the inner scrollbars break.
- **Tablet (761–1150 px):** the map is on the left, and both sidebars are stacked on the right, each scrolling on its own.
- **Phone (≤ 760 px):** one column with the map first. The building details become a **bottom sheet** that slides up (`.sheet-open`) and has a ✕ close button. Nav buttons get larger tap targets.
- 📂 `style.css`: the `@media (min-width: 761px)` block at the end of the file, plus the `@media (max-width: 760px)` block.

## Why we built TigerQuest this way

| Decision | Why it fits a hackathon prototype | Where it becomes limiting in production |
|---|---|---|
| **Vanilla JavaScript instead of React** | No build tools, runs by double-click, every line is visible and explainable, fewer moving parts to break during a live demo | Large teams and complex interfaces benefit from components, state management and tooling |
| **Static website instead of full-stack** | Free to host, nothing to deploy or keep running, works offline | No shared data, no accounts, no trusted actions |
| **localStorage instead of PostgreSQL / Firebase** | Zero setup; progress survives refreshes; no personal data leaves the device | Can't sync devices; users can edit their own XP; no analytics for the university |
| **SVG hotspots instead of a game engine** | Uses the illustration directly; scaling, clicks, keyboard focus and styling are built in | Complex animation, physics or a large tile-based world would suit an engine |
| **Waypoint graph instead of a navigation system** | 43 points we can see and reason about; Dijkstra runs in ~1 ms; easy to debug visually with `#debug` | Real campus navigation needs accurate sidewalk data, accessibility routes and real geography (GIS) |
| **Public calendar feed instead of a private integration** | No credentials, no approval process, real data on day one | Depends on the public feed; no guaranteed terms, uptime or matching quality |

## 11. Limitations & future development

Full list: [PROJECT_LIMITATIONS.md](PROJECT_LIMITATIONS.md). The ones that matter most:

1. **Simulated verification.** Biggest gap. *Next:* QR check-in or organizer confirmation, with a backend.
2. **Browser-only storage, no authentication.** No syncing; XP can be edited by hand. *Next:* accounts and a server-side database where only the server awards XP.
3. **External event dependency and approximate matching.** *Next:* an official feed, a building-code lookup table, server caching.
4. **Limited coverage:** 11 buildings with general descriptions.
5. **Mobile and accessibility** work but aren't fully tested (no real-device or screen-reader testing).
6. **Scalability:** content is hard-coded in `script.js`.

## 12. Glossary

| Term | Meaning | In TigerQuest |
|---|---|---|
| **Frontend** | Code that runs in the user's browser | All of TigerQuest |
| **Backend** | Code on a server shared by many users | None. A future version would need one for accounts and verification |
| **API** | A defined way for programs to request data from each other | `events.towson.edu/api/2/events` gives us event data |
| **HTTP** | The protocol browsers use to talk to servers | `fetch()` sends an HTTP GET request to the events API |
| **JSON** | Text format for structured data | The API's reply, and our saved progress |
| **DOM** | The browser's live tree of page elements | `renderDetails()` updates DOM elements like `#detailName` |
| **SVG** | Scalable vector graphics in markup | The map container, building polygons, character, badges |
| **Event listener** | A function the browser calls when something happens | Clicks on hotspots call `selectBuilding()`; `keydown` updates `keysHeld` |
| **Algorithm** | A step-by-step procedure to solve a problem | Dijkstra's algorithm in `findPath()`; ray casting in `isPointInPolygon()` |
| **Graph** | Nodes connected by edges | The walking network |
| **Node** | A point in a graph | Waypoint `n` at (808, 505) |
| **Edge** | A connection between two nodes | `['n','ao']`, a walkable straight line |
| **Waypoint** | A node placed on a path | 43 waypoints in `WAYPOINTS` |
| **Dijkstra's algorithm** | Finds shortest paths in graphs with non-negative weights | Union → Liberal Arts goes through `n` and `ao` |
| **requestAnimationFrame** | Browser API that runs code before each repaint | Drives `gameLoop()` about 60×/s |
| **localStorage** | Per-site key-value text storage in the browser | `tigerquest-save-v2` |
| **Responsive design** | One page adapting to different screen sizes | Three columns, then two, then one, with a bottom sheet on phones |
| **CORS** | Browser rule controlling which sites may read data from other sites | Towson's API allows it (`*`); Involved@TU's JSON endpoint does not |
| **Static website** | Fixed files served as-is, no server-side code | Our 3 files + 1 image |
| **Client-side rendering** | The browser builds the page's content with JavaScript | Event cards and mission cards are built as HTML strings in `script.js` |
| **Promise / async-await** | A way to wait for slow work without freezing the page | `await fetch(...)` in `loadLiveEvents()` |
| **Regular expression** | A pattern for matching text | `LOCATION_RULES` match "UU 222" to the Union |
| **viewBox** | The part of an SVG's coordinate system that is visible | Zoom changes the viewBox |
